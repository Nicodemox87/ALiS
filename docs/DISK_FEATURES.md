# Disk-only geometric features — public alpha.5.21

This workflow is included in the public Windows alpha.5.21 release. The development notes below trace the earlier local alpha.5.11–5.14 changes; they are not evidence of a matching Mac release. For current in-cloud output, recovery and resume instructions see the [user guide](USER_GUIDE_IT.md#9-feature-a-blocchi-salvataggio-recupero-e-resume). Updating macOS is the next roadmap step.

## Use

1. Select the existing cloud in CloudCompare. Choose features and radii in Prepare → Features.
2. Open **Spatial blocks**. If full-cloud fields would not fit safely, **Disk only (bounded RAM; linked features)** is selected automatically. Large direct feature requests also open this panel.
3. Choose a writable output folder with enough disk space. **Automatic RAM and adaptive sub-blocks** is enabled by default. It reserves RAM for CC, the OS and other applications and rechecks free RAM before each processing sub-block. **Suggest grid from this PC / cloud** uses available RAM, density, feature count and halo; it does not change an existing job's grid. Dense map blocks are split internally from exact context counts, not merely average density. Exact radii are never silently reduced and points are not decimated.
4. Run selected blocks progressively. Disk-only mode adds **no new full-cloud SF arrays and no geometry clone**. Each original core row is journalled once; halo is temporary and excluded from committed results.
5. Save the BIN project normally to retain links to the external job. Keep the **whole output folder** with the BIN: the BIN references journals, it does not embed their feature values. Reopen the same unchanged BIN and panel to resume completed cores. If the BIN predates processing, select the identical grid/features and the existing folder: every completed checkpoint is checked against ordered-geometry identity, schema, row IDs and SHA256 before recovery. Old alpha.5.10 completed blocks remain compatible.
6. Use **Export unified LAS from disk features…** when needed. A bounded snapshot reads current CC coordinates, SFs, RGB and normals; an isolated Python exporter writes one LAS with new Extra Bytes. It retains every source point and leaves features of unprocessed rows NaN. It does not load the result automatically.

The original loaded cloud stays in CC's RAM. In-cloud modes still require approximately `4 × point count × field count` additional bytes. Disk-only mode removes that **additional feature-array** requirement; it cannot make already-loaded geometry disappear from memory or guarantee that any arbitrarily dense halo fits.

## Adaptive subdivision and time estimation

Map blocks remain the selectable/reporting units (for example 100 × 100 m). A temporary disk spool retains original row IDs and full-resolution coordinates. Processing recursively quarters a dense core until its complete halo fits a conservative budget. Each child reads context from the parent spool; half-open cores assign each source row once. At most four sorted child journals are merged at a time, with bounded buffers, into the original parent checkpoint. No whole-parent feature matrix is allocated, even for a very large map core. Temporary halo, child geometry and intermediate journals are removed with their private scratch directory after success/cancellation; source and previously committed parent files are not deleted.

From local alpha.5.12, automatic worker RAM is at most 50% of currently available RAM and 24 GiB, retaining at least 2 GiB and 40% of available RAM as reserve. Manual ceilings can be entered up to 64 GiB but remain bounded by current free RAM with at least 2 GiB and 25% retained. These are ceilings, not reservations or forced allocations. More memory reduces subdivision/context overhead only when it changes the safe processing size. CPU threads are selectable and persisted independently of the job identity; the default is up to 24, leaving two logical processors available where possible, and the engine accepts at most 32. Extra thread scratch is included in the worker preflight. Parameter changes do not invalidate completed feature checkpoints. GPU acceleration is not introduced for geometric features: an isolated CUDA prototype is not a production backend. The memory model is conservative and not an OS-enforced quota. A halo that alone exceeds capacity (e.g. extremely dense coincident points and a very large radius) stops with an explicit diagnostic after bounded recursion, never by truncating context or discarding points.

The pilot and the first run begin near the median point count of selected unfinished map blocks, rather than the first nearly empty survey corner. The elapsed wall time includes collection, worker processing and checkpoint commit. Completed cores with at least 10,000 points calibrate throughput using `work = points × (1 + points / core XY area)` as a density-aware scheduling heuristic. While the first parent is unfinished, completed processing sub-blocks provide an explicitly **provisional** estimate; full parent timings supersede it when available. Remaining/total time is shown as a wide interval (initially 0.4–2.5 times the measured projection, then 0.6–1.8 after three calibration blocks), refreshed during processing. This is not an accuracy guarantee or a machine-learning performance model; CPU load, point distribution, halo overlap and storage affect it. Before a useful benchmark, the UI explicitly says that calibration is pending rather than inventing a duration. Timings, leaf counts and evaluated context counts are recorded per block in `blocks.json`. A stopped, uncommitted parent is recomputed on resume; completed parent checkpoints are skipped.

## Persistence, integrity and outputs

Local alpha.5.13 retains this block workflow but distinguishes **core queries** from **halo support**, as in the 3DMASC core/support design: every full-resolution core point receives features; the full requested halo remains in the octree, but its own feature rows are not calculated just to be discarded. An explicit sorted `query_indices.u32` scratch file defines the core rows. These partial worker caches cannot be reused as complete-cloud caches. Nothing is subsampled and no labels are changed. Multiscale covariance/height prefixes, per-cell buffer reuse, exact percentile-rank selection, symmetric quadric accumulation and covariance-derived projected moments reduce repeated work; near-degenerate moments retain the direct path. A failed PCA decomposition is retried with only scale-relative round-off-sized off-diagonal terms cleared. Thus mathematical feature definitions remain the same, but floating-point results are not promised bit-identical; regression comparisons use explicit tolerances.

The adaptive capacity model now uses a conservative field/context cost (`240 + 8 × field_count` bytes per support point), plus 256 MiB fixed headroom and separate thread scratch (`96 × threads × min(context_points, 200000)`). The native worker retains its own independent preallocation guard. This avoids multiplying maximum search scratch by the whole million-point context. Dense contexts can still split; all safeguards remain. **ALiS scales are radii**: 3DMASC `SC4` denotes diameter 4 m, corresponding to ALiS radius 2 m. Resuming an existing job does not halve its radii.

`blocks.json` records the processing version and the engine version for newly completed parents. An empty engine version on a retained older parent means it was not previously recorded; no provenance is invented. Checkpoint format and geometry/schema identity remain compatible, so verified completed parents are retained. See [source audit and measured validation](VALIDATION_CORE_SUPPORT_LOCAL.md).

The next UI build displays elapsed time and both ends of remaining/total duration ranges as `05 h 53 min`, rounded to the nearest minute. Hours do not wrap at 24. **Estimated total (this run)** includes elapsed time since this processing pass started, not historical time spent on earlier sessions. This changes presentation only, not the density-aware estimator or its uncertainty range. A running CloudCompare instance is not hot-replaced or interrupted to apply this display-only update.

- `*.alsf`: sorted source row IDs and feature values, no geometry/halo copies.
- `disk_features.json`: exact feature/radius schema, ordered global-XYZ fingerprint, completed cores and SHA256 of each journal.
- `blocks.json`: grid, selection, progress and errors.
- `export_snapshot.bin/json`: bounded-write export snapshot of current CC attributes. It occupies disk, not a second cloud in RAM. Retained for provenance/re-export; keep the linked job folder.
- Exported `*.las` and `*.features.json`: current attributes, feature-name aliases, coverage counts, coordinate precision and readable CC metadata. A mapping VLR/EVLR is embedded in LAS and recognized by model-driven disk preparation when existing features are explicitly reused.

LAS exports use version 1.4/point format 7 and adaptive coordinate quantization (normally 0.0001 m). Original SFs/normals are retained as float Extra Bytes; current CC byte colours are multiplied by 257 into LAS RGB. Available intensity/return integer attributes are mapped into native fields as well as preserved as SFs. ASPRS Working is preferred for native Classification, with original/current classification as fallback. Invalid noninteger/out-of-range labels are rejected, never truncated. This does not certify training labels.

An explicit `LAS.projection` coordinate-system WKT is preserved if present. No missing CRS/EPSG is invented. LAS attributes that were never loaded into CC, opaque source VLRs or original 16-bit RGB precision cannot be recovered from a CC snapshot. Preserve the original LAS and BIN. This is an export of the **current CC representation**, not a claim of lossless copying of the original sensor file.

The exporter uses bounded source chunks, at most 32 MiB for its feature matrix and a shared 64 MiB reader-buffer budget, plus bounded LAS/NumPy/Python overhead and at most 64 open checkpoint handles. It never maps or allocates the entire `N × K` feature matrix. Every checkpoint is streamed, row-ownership and geometry hashes are checked before atomic LAS replacement. Corruption/overlapping cores fail without replacing a previous LAS. Partial export is allowed but reported explicitly as NaN coverage.

The existing in-memory training-subset action is disabled in Disk-only mode so it cannot silently omit externally stored features. Exported features can be reused in model-driven disk preparation; out-of-core model training and lazy display of full-cloud external SFs are separate future work. Current cloud/copy modes retain their existing training subset behavior.

Choosing a new **empty** job folder starts an independent disk job without deleting old journals. Do not manually edit/reorder geometry, journal files or schema. A BIN without its external job folder cannot reconstruct these disk-only features.
